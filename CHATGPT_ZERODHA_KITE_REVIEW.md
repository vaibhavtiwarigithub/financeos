# ChatGPT Zerodha/Kite API Path Review — 2026-07-07

Scope reviewed: Zerodha/Kite direct routes, Kite helper/adapter, India dashboard order UI, generic broker gateway integration, order sync/reconciliation, and broker/account settings. This is a code/logic/security review only; no production code was changed.

## Findings

| # | Severity | File | Location | Issue | Suggested Fix |
|---|---|---|---|---|---|
| 1 | BLOCKER | `app/api/kite/order/route.ts`, `app/dashboard/india/page.tsx` | `route.ts:14-57`, `page.tsx:139-156` | Direct real-money Kite orders bypass the hardened Execution Gateway. The India UI posts straight to `/api/kite/order` with `confirm:true`, and that route calls `placeEquityOrder()` directly. This skips the protections present in `/api/broker/orders`: owner gate, `guardOrderRequest`, global/per-market kill switches, `trading_enabled_india`, active broker/account allowlist, notional cap, price-drift recheck, duplicate-submit protection, broker order ledger, and sync/reconciliation. Failure scenario: browser/session compromise or a UI bug submits `{symbol:"RELIANCE.NS", transaction_type:"BUY", quantity:1000, confirm:true}` and the app sends a live Kite order without the gateway controls. | Remove or disable `/api/kite/order` as an execution endpoint. Route India live orders through `/api/broker/orders` using `active_broker_india="kite"` and a `trade_proposals` / approval flow, or move every gateway guard into the Kite route before any broker call. Prefer one execution choke point for all live orders. |
| 2 | BLOCKER | `app/api/kite/order/route.ts` | `15-16` | Real-money order placement only checks “any authenticated user”, not the configured single owner. Other sensitive Kite routes use the same weak pattern. If any non-owner account can authenticate, it can place, view, or disconnect Kite. This conflicts with the Robinhood gateway standard (`requireOwner()`) and the single-user safety model. | Replace `createClient().auth.getUser()` auth-only gates with `requireOwner()` on `/api/kite/order`, `/api/kite/login`, `/api/kite/status`, `/api/kite/portfolio`, and `/api/kite/disconnect`. Keep callback special, but bind it with state as described below. |
| 3 | BLOCKER | `app/api/kite/order/route.ts` | `14-34` | No CSRF / origin / DNS-rebinding guard on the live-order route. The hardened gateway calls `guardOrderRequest(req)` before processing; `/api/kite/order` does not. Because the route accepts JSON with `confirm:true`, a same-site/cookie-bearing malicious page or local-network attack path can attempt a real order if browser protections are insufficient. | Add `guardOrderRequest(req)` before reading the body, exactly like `/api/broker/orders`. Better: remove this route and reuse the gateway, which already has the guard. |
| 4 | HIGH | `app/api/kite/order/route.ts`, `app/api/broker/orders/sync/route.ts` | `order.ts:43-57`, `sync.ts:21-90` | Direct Kite orders are not inserted into `broker_orders`, so the broker sync loop cannot track, reconcile, cancel, or detect ambiguous statuses for them. The only audit is a best-effort `decision_journal` insert that is swallowed on failure. Failure scenario: order succeeds at Kite, `decision_journal` insert fails, and Kairos has no durable order id ledger; later sync cannot update fill status or detect drift. | Every live order must create a `broker_orders` row before broker submission and update it after submission. Use the generic gateway’s pre-insert / submit / status update flow. Make audit insert failures non-fatal only after the durable order ledger exists. |
| 5 | HIGH | `app/api/kite/order/route.ts`, `app/dashboard/india/page.tsx` | `route.ts:19-39`, `page.tsx:365-375` | Kite SELL orders have no “sell-only-if-held” check. The UI exposes BUY/SELL, and the route accepts `transaction_type:"SELL"` without verifying current holdings or quantity. Zerodha may reject some invalid sells, but the app should fail closed before broker submission, especially under a long-only policy. | Before any SELL, call `getKiteHoldings()` and require `heldQty >= requestedQty` for the exact symbol/exchange. Implement this in the gateway using a broker holdings abstraction, not only in UI. |
| 6 | HIGH | `app/api/kite/order/route.ts` | `19-39` | No order notional cap or quote/price sanity check for Kite direct orders. A typo in quantity can create an oversized market order because the route never estimates `qty * current price`, never checks `max_order_notional`, and never revalidates price drift from proposal to approval. | Reuse gateway notional checks for India. Fetch a fresh India quote before submission; fail closed if quote is unavailable; require `qty * quote <= min(max_order_notional, configured equity fraction)`. For LIMIT orders, also validate limit-vs-quote drift. |
| 7 | HIGH | `app/api/kite/callback/route.ts`, `lib/kite.ts` | `callback.ts:7-33`, `kite.ts:34-57` | Kite OAuth/login callback has no `state` value and is not bound to the initiating owner session. The comment says no auth gate is intentional, but without state the app cannot prove the callback belongs to the login flow started from this browser/session. Failure scenario: a request token from a different Kite login for the same API app could be exchanged and stored as the app’s active token. | Add an HMAC-signed, HttpOnly, short-lived `kite_oauth_state` cookie in `/api/kite/login`; include `state` in the Kite login URL if Kite supports it. In callback, verify state and then call `/user/profile` after exchange; only store the token if the Kite `user_id` / email matches a configured allowlist. If Kite Connect does not echo `state`, store a one-time login nonce server-side and verify the returned profile before committing the token. |
| 8 | MEDIUM | `app/api/kite/order/route.ts`, `lib/kite.ts` | `order.ts:19-34`, `kite.ts:199-214` | Runtime input validation is too loose for a live-order path. TypeScript annotations do not validate JSON. `transaction_type`, `order_type`, `symbol`, `quantity`, and `price` can be wrong types or non-finite values. In the helper, `Math.max(1, Math.floor(opts.quantity))` silently turns low positive values into `1` and lets `NaN` become `"NaN"`. Failure scenario: upstream code passes `quantity:0.2` or `quantity:NaN`; helper does not reject and may submit an unintended or malformed live order. | Add a strict schema validator at the route boundary: symbol regex + supported suffix/exchange, side enum, order type enum, integer quantity `>=1`, finite positive price when required. In `placeEquityOrder()`, remove silent clamping and throw/return `{ok:false}` for invalid quantity/price. |
| 9 | MEDIUM | `lib/brokers/adapters/kite.ts` | `21-31` | Kite adapter treats a successful broker response with missing `order_id` as success. It returns `{ok:true, brokerOrderId: undefined}`; the sync route later skips rows without `broker_order_id`, leaving an untrackable live order. | After `placeEquityOrder()`, require a non-empty string `res.data.order_id`. If missing, return `{ok:false, needsReconcile:true, error:"Kite order accepted but order_id missing"}` or the project’s equivalent ambiguous-status result so the gateway marks `unknown_needs_reconcile`. |
| 10 | MEDIUM | `lib/brokers/adapters/kite.ts`, `lib/kite.ts` | `adapter.ts:15-19`, `kite.ts:75-81` | `kiteAdapter().isConfigured()` only checks API key/secret, not whether today’s access token exists and is fresh. The generic gateway may show Kite as configured and proceed until `authHeaders()` fails. This is safe-ish, but misleading and creates late failures. | Change `isConfigured()` to require `apiKey`, `apiSecret`, and `getAccessToken().fresh`. Expose a separate “credentials configured but daily login required” status for UI. |
| 11 | MEDIUM | `app/api/broker/orders/route.ts` | `182-190` | If Kite is routed through the generic gateway, the non-Robinhood SELL check currently reads `live_account_snapshots.positions_json`, which is Robinhood/live-snapshot shaped and not Kite holdings. That can either block valid Kite sells or verify against the wrong source. | Add a broker adapter capability such as `getHeldQty(symbol)` and use it for SELL checks. Implement Kite with `getKiteHoldings()`. Keep Robinhood using `robinhoodHeldQty()` for live MCP. Do not use generic snapshots for broker-specific live holdings. |
| 12 | MEDIUM | `supabase/migrations/093_broker_accounts_and_robinhood_mcp.sql`, `app/api/broker/orders/route.ts`, `app/api/settings/risk-profile/route.ts` | `orders.ts:30-46`, `settings.ts:132-140` | The hardened gateway requires `strategy_config.active_account_india` and a `broker_accounts` allowlist row, but the migration seed was Robinhood-focused and appears not to seed a Kite trading account. If the direct route is removed today, Kite gateway execution likely fails closed until a Kite account row/config exists. Also, settings validation checks `account_number` + `market` but not `broker`, so duplicate account numbers across brokers could validate incorrectly. | Add a Kite account/profile allowlist row after verifying the Kite profile (`broker='kite'`, `market='india'`, role=`trading`, account/user id from Kite). Set `active_account_india` through owner-gated settings. In settings validation, filter by `broker` matching `active_broker_india`/`active_broker_us` as well as `market` and `account_number`. |
| 13 | MEDIUM | `app/api/kite/status/route.ts`, `app/api/kite/portfolio/route.ts`, `app/api/kite/disconnect/route.ts`, `app/api/kite/login/route.ts` | `status.ts:12-28`, `portfolio.ts:10-27`, `disconnect.ts:16-20`, `login.ts:11-18` | Sensitive Kite operations and PII/holdings reads are auth-only, not owner-only. `/api/kite/status` can expose Kite profile name/email; `/api/kite/portfolio` exposes holdings/P&L; `/api/kite/disconnect` can wipe the active token. In a single-user app this may seem low-risk, but the rest of the live-trading path has moved to owner gates. | Use `requireOwner()` consistently for all Kite routes except the callback, which should be protected by login state + profile allowlist. |
| 14 | LOW | `lib/kite.ts` | `75-81`, `124-139` | Token freshness is based on the UTC calendar date, but Kite tokens are tied to the Indian trading day/session. Around timezone boundaries, the app can mark a token stale/fresh based on UTC rather than Kite’s actual validity. The subsequent Kite API call will still fail if invalid, so this is mostly reliability/UI noise. | Track `KITE_ACCESS_TOKEN` with an explicit `expires_at` or validate via `/user/profile` when status matters. If keeping date logic, compare in `Asia/Kolkata` and still fail closed on any Kite auth failure. |
| 15 | LOW | `lib/kite.ts` | `91-118` | `disconnectKite()` sends `access_token` in the query string because Kite’s endpoint expects it. This is probably unavoidable for that API, but URLs are more likely than headers to appear in infra/proxy logs. | Keep the call if required by Kite, but ensure no app-level logging captures the full URL. Consider wrapping this with a “never log request URL” helper/comment and redact `access_token` in any fetch-error telemetry. |

## Clean / acceptable observations

| Area | Assessment |
|---|---|
| `api_key_vault` storage | Current project history indicates the vault was locked down to service-role-only in migration 089. That materially reduces token exposure risk, assuming the live database has that migration applied. |
| Kite helper does not log raw tokens | I did not see token values being printed or returned from API responses. |

| Generic broker sync has a Kite reconciliation path | `app/api/broker/orders/sync/route.ts` now attempts Kite holdings reconciliation for `broker_orders` rows. The gap is that the direct `/api/kite/order` route bypasses that ledger entirely. |

## Recommended fix order for Claude

1. **Close the direct execution bypass first.** Disable `/api/kite/order` or convert it into a thin wrapper around `/api/broker/orders`; update `app/dashboard/india/page.tsx` to submit proposals/gateway orders, not direct broker calls.
2. **Owner + request guard everywhere.** Apply `requireOwner()` to Kite routes and `guardOrderRequest()` to any live-order POST that remains.
3. **Make Kite a first-class broker in the gateway.** Seed/validate the Kite account allowlist, require fresh daily token in `isConfigured()`, add broker-specific held-quantity support, and ensure every live Kite order creates/updates `broker_orders`.
4. **Harden order validation and ambiguous outcomes.** Strict JSON schema, no helper-level clamping, require broker `order_id`, and mark missing/uncertain broker responses as `unknown_needs_reconcile`.
5. **Add callback binding.** Add state/nonce plus post-exchange Kite profile allowlist before storing `KITE_ACCESS_TOKEN`.

Bottom line: the Kite API helper is mostly straightforward, but the current app architecture has a dangerous split-brain execution design. Robinhood/live gateway hardening does not protect India orders while `/api/kite/order` remains callable from the UI.

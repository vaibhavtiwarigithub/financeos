# Supabase cold archive and sub-400 MB recovery — detailed design

Status: owner approved with “go” on November 16, 2026. Codex is assigned Architect and Builder. The full database snapshot and three table/cohort archives are copied to private R2 and verified; matching cold history was removed only after restore and reader checks. The database remains over quota and the app archive path is still in progress.

## 1. Goal and constraints

Reduce Kairos's active Supabase database to a measured target below 400,000,000 bytes while retaining complete, auditable access to historical research and evaluation evidence through private Cloudflare R2 archives. Preserve Supabase Postgres as the only transactional/query engine for live Kairos features. The archive is a cold-data tier; it is not a second writable database and does not alter trading, score, strategy, position, broker, or council settings.

R2 is verified as a private archive destination: account access, bucket inventory, authenticated Wrangler upload, download, and checksums have been verified. No new paid service, credential extraction, or public bucket access is part of this design. D1 is excluded from the primary archive because it would require a second SQL data model and does not provide Postgres semantics or a transparent substitute for current Supabase joins/functions/RLS.

## 2. Measured basis and target math

The read-only baseline before pruning (2026-11-16 08:15 UTC) was `pg_database_size = 1,099,115,667` bytes, with transaction and default read-only both off. Verified production reclamations and content-preserving compaction first reduced it to 847,203,475 bytes (11:03:20 UTC), then to 828,443,795 bytes (11:45:56 UTC) after the seven-day India news snapshot cohort was archived and reclaimed. Total measured savings are 270,671,872 physical bytes. The remaining reduction is at least 428,443,795 bytes to cross 400,000,000 bytes, before ongoing writes and further physical reclamation. A practical target is 380,000,000 bytes or less, leaving 20 MB of headroom. Recompute from a fresh measurement before each cohort; row payload sums are not a prediction of reclaimed database bytes.

Largest observed relations include price-cache restatements (~118.9 MB), symbol daily returns (~90.6 MB), decision observations (~80.0 MB), price cache (~66.3 MB), research packets (~62.9 MB), observation labels (~46.3 MB), evidence records (~45.5 MB), signal-score history (~42.0 MB), and dimension diagnostic findings (~39.9 MB). These values include relation/index/TOAST effects as reported in the prior audit and must not be added as though they equal reclaimable disk. The archive plan must use exact fresh table, index, TOAST, row-count and database-size measurements.

## 3. Data lifecycle and archive format

### 3.1 Immutable archive objects

Use a private R2 Standard bucket, with server-side S3-compatible access only. Archive batches are immutable, gzip-compressed PostgreSQL-compatible row data, split into bounded chunks by table and UTC month (and market where applicable). Deterministic content-addressed object keys include dataset/table, schema version, partition, and SHA-256. No browser/client access and no public bucket.

Each signed-off manifest records source project identifier (not credentials), relation/schema fingerprint, export timestamp and cutoff, primary-key range, row count, null/duplicate checks, chunk sizes and SHA-256 hashes, canonical dataset fingerprint, exporter version, and restore receipt. R2 metadata is not the sole index: keep a small Supabase archive catalog containing manifest ID, object keys, checksums, table/partition, row range/count, schema fingerprint, and verification state. The catalog must not contain row payloads or secrets.

Export uses a consistent read snapshot and bounded batches. Every completed chunk is downloaded again and hash-checked. Restore verification loads into an isolated PostgreSQL 17 database and checks exact row counts, ordered-key digests, schema compatibility, foreign-key/orphan checks, representative point reads, and cross-table joins. Existing local cache archive tools are a reference implementation for integrity, not a claim that durable tables have been exported.

### 3.2 R2 hard budget


Use an 8,000,000,000-byte (8 decimal GB) account-wide maximum, below Cloudflare R2 Standard's 10 GB-month free allowance. The uploader must inventory every bucket and every paginated object before upload, estimate payload plus the documented maximum 8,192-byte metadata allowance per object, and stop at 7,500,000,000 projected bytes. Warn at 6,000,000,000 bytes. Refuse if inventory is missing, stale/invalid, or fails. After upload, reconcile account metrics and inventory; do not delete unique archives to stay under the cap. The local uploader takes an exclusive lock to prevent concurrent runs from this machine. Since Cloudflare does not expose a provider-enforced storage quota and other credentials/dashboard uploads can bypass this script, the 8 GB cap is guaranteed only when all writes go through the guarded single-writer workflow; any bypass invalidates the guarantee. Keep archive operations small (bounded chunk count) to remain well within included free operation quotas; never allow a paid service or automatic overage.

### 3.3 Data retrieval

R2 does not support SQL queries. For interactive historic evidence, only introduce an authenticated server-side archive reader after table-specific contract tests: resolve IDs/partition through the compact catalog, fetch relevant immutable chunk(s), validate object hash, parse bounded rows, and return the same typed domain records. Do not route unfiltered dashboard/table scans through R2. For analytical jobs and joins, restore selected partitions to isolated PostgreSQL staging, execute the existing query semantics there, and return only bounded results. Archive miss, schema mismatch, timeout, or checksum failure returns an explicit degraded result; it must not silently return empty history or alter scores.

### Phase 4 — controlled online pruning and physical reclamation

Only after full-DB restore, exact archive restore, reader parity, and a cohort-specific safety audit pass: transactionally remove the archived source cohort in bounded batches with lock/statement timeouts, stable PK ranges, and stop-on-error. Production pruning remains a data-safety gate, not a second permission prompt: only execute cohorts whose archive, exact source rows, recovery path, and application behavior are verified. Do not run pruning automatically from the daily monitor.

## 5. Automated Supabase budget guard

The monitor runs at least daily through an already-scheduled low-impact health path and before any archive/prune operation. It records a daily series with timestamp, database bytes, major relation bytes, recent delta, estimated time to 400MB/500MB, and monitoring status. It sends one deduplicated owner alert at 350MB, escalates at 380MB, and records a breach at 400MB. Because essential producers can exceed budget between daily samples, a hard limit additionally requires pre-write admission checks or bounded retention for each nonessential producer; do not claim daily monitoring alone guarantees staying below 400MB. Fail monitoring visibly when size query is unavailable. Do not invoke research/trading routes to test the monitor.

## 9. Hosting and database platform alternatives (owner follow-up, November 16, 2026)

### Why Render was suggested, and what that does/does not solve

The likely rationale for suggesting Render was that it runs Kairos as a conventional Node.js Next.js web service, avoiding some serverless invocation/active-CPU accounting while keeping the current Node runtime model. That is a compatibility advantage, not proof that it is the better free production host. Render's current free web services sleep after 15 minutes idle, take about a minute to wake, share 750 free instance-hours per workspace/month, use ephemeral filesystems, and Render says free instances are not for production. External service-initiated traffic can also cause a free service to be suspended. The previous recovery-mode dashboard demonstrates that “same GitHub repo” alone does not guarantee parity; commit, build/start commands, environment variables, auth callbacks, cron and service configuration must all match. Exact cause of that Render dashboard failure must be verified from its deployment/runtime evidence, not guessed from host choice.

Therefore Render remains useful as a compatibility mirror or preview, not the recommended permanent free production answer for this always-on, scheduled app. It changes the resource failure mode from Vercel function CPU consumption to sleeping, workspace hours, outbound traffic, and operations limits; it does not remove compute work.

### Cloudflare Pages versus Cloudflare Workers for Kairos

Kairos is a dynamic Next.js 15 App Router application, with Supabase cookie auth, server components, over 2,000 table-query call sites in app/lib, many Postgres RPC dependencies, and 27 configured Vercel cron routes. A static Pages export cannot preserve these server routes, authenticated SSR, or server-side jobs. Cloudflare now directs full-stack Next.js applications to Workers and says Pages is the static-export path. The current Workers default recommendation, `vinext`, is explicitly beta; Cloudflare lists App Router, route handlers, SSR, middleware and Server Actions as supported, but requires a compatibility check and describes some imports as “mostly supported.” The existing Next 15 app is therefore a plausible migration candidate, not yet proven drop-in equivalent.

Workers Free currently allows 100,000 requests/day but only 10 ms CPU per HTTP request and 10 ms per Cron Trigger, with five Cron Triggers/account. Kairos's current `vercel.json` has 27 cron routes, including heavier agent/evaluator work; consolidating schedules does not make heavy CPU functions fit the free 10 ms limit. Network wait does not count as CPU, so lightweight SSR/API handlers may fit, but CPU-heavy query processing, JSON serialization, and agent logic may exceed it. A Cloudflare Workers Paid subscription starts at $5/month; it includes 30 million CPU milliseconds/month, 10 million requests and higher Cron limits, then bills by usage. Cost and capacity would need measurement against Kairos's actual invocation profile. Workers may still be an attractive later host after a vinext compatibility test and cron redesign, but not a guaranteed zero-cost cure.

The current application’s local Claude CLI bridge is deliberately host-local and is not a deployable cloud runtime dependency; Vercel already cannot run it. Cloudflare migration must preserve the existing behavior where that feature is unavailable remotely, rather than introducing a new CLI assumption.

### D1 + R2 is not automatic tiering or a drop-in Supabase replacement

D1 is managed SQLite and R2 is object storage. Cloudflare does not automatically age D1 rows into R2. To maintain a hot/cold split, Kairos would need to build and operate: retention policy by table, consistent export, immutable archive manifests/checksums, verified upload, catalog/index, deletion gate, R2 read/restore adapter, replay/staging for relational queries, orphan/FK handling, and a reconciler. Writes and reads that cross D1 and R2 do not share a database transaction. Restoring a historical partition for a join would be a deliberate workflow, not a transparent SQL query.

D1 Free permits 10 databases, 500 MB each and 5 GB aggregate, with 5 million rows read/day and 100,000 rows written/day. Exceeding daily quotas stops D1 queries until reset. Each database processes queries single-threaded; D1 is designed to scale by partitioning across smaller databases, which would complicate Kairos's joins and foreign-key relationships. D1's paid plan removes several free limits, but is not synonymous with keeping the entire workload free. R2 Standard currently includes 10 GB-month free and no egress fees; the account still needs R2 entitlement, and usage above included amounts is billable.

Moving Kairos from Supabase to D1 would require replacing the existing `@supabase/supabase-js` / `@supabase/ssr` data/auth access, converting PostgreSQL SQL and migration files to SQLite, rewriting Postgres functions/RPCs and triggers, replacing database-enforced RLS authorization, and redesigning pgvector-backed memory/search (if enabled). The repository has many PostgREST calls and migrations; a query-site count alone understates effort because several RPCs implement critical atomic behavior. Splitting historical data to R2 reduces storage only after these replacements and all parity checks. The conversion would be a high-risk app/database rewrite, not a hosting toggle.

### Recommendation

1. **Now:** keep Vercel + Supabase as the behaviorally proven primary while measuring and reducing Vercel CPU at its source; keep Render as a preview/mirror only if it passes full parity and stays within free constraints. Do not move production to Pages or D1 during storage recovery.
2. **Storage:** continue the Supabase + private R2 cold-archive design. The full restore and private R2 copies are verified. Keep active queryable data, SQL joins and safety-critical records in Postgres; archive history only after tested readers/restore preserve current behavior. This targets the actual Supabase DB-size issue with the smallest data-layer change.
3. **Cloudflare host option:** separately run a non-production vinext compatibility/build/route audit against a deployment preview using the existing Supabase DB. If tests pass, estimate CPU per request and redesign/split the 27 cron tasks; only then compare Cloudflare Workers Paid (likely at least $5/month) with Vercel. Pages is suitable only for a static subsite or marketing shell, not as the full current app runtime.
4. **D1 + R2:** defer unless there is a deliberate funded project to port and own the database/auth layer. A future hybrid could use D1 for a deliberately small operational schema and R2 for explicit cold archives, but must not promise automatic row lifecycle, transparent SQL, or continued Supabase semantics.
